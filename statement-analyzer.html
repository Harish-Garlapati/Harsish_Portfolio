case study

Multi-bank Statement Analyzer: from 30 minutes to under 2.

How I built the statement analysis engine inside a lending company's loan CRM, and why most of the work was proving the numbers were right.

Role

Built the Python engine + CRM integration

Timeline

Jun 2026 – present

Stack

Python, pdfplumber, OCR, Node.js, Angular, MySQL

Status

Live in production

The problem

Before approving a loan, the credit team needs to know how money actually moves through a borrower's account: monthly credits, debits, average balance, EMIs, bounced cheques. That means reading every line of 6 to 12 months of bank statements.

Done by hand, one file took at least half an hour. And every bank lays out its PDFs differently: different columns, date formats, multi-line narrations, and some statements are scanned images rather than text.

The constraint that shaped everything

In lending, a wrong number is worse than no number. A tool that is right 98% of the time but quietly invents a balance 2% of the time is dangerous, because nobody re-checks it.

So I made one rule early: numbers are extracted with deterministic, rule-based parsing and verified against the statement itself. AI helps me build faster, but it never gets to guess a figure.

The approach

I built a Python engine that runs alongside the CRM's existing Node.js backend, with a six-stage pipeline and bank-specific templates layered on top:

Token extraction + OCR→ Row building→ Column detection→ Normalization→ Validation→ Excel / CRM output

The validation stage is the heart of it: every row's balance must follow from the previous balance plus credits minus debits. If it doesn't, the statement is flagged instead of silently passed through.

The bugs that mattered

When I audited the parsing pipeline, I found four problems. None of them threw an error, which is exactly what made them dangerous.

1. Silent data corruption on detailed statements

One large bank's "detailed statement" layout was being read with a line-based extractor that scrambled rows without any warning.

Fix: a new table-based extractor and a routing step that sends each layout to the right parser.

2. Double-counting across overlapping statements

When a borrower uploaded PDFs covering overlapping dates in different layouts, the same transactions were counted twice.

Fix: rewrote de-duplication to compare normalized date, amount and balance instead of raw text.

3. Intermittent crashes on one bank's files

A native PDF process occasionally crashed on one bank's statements, failing uploads at random.

Fix: automatic retry logic in the Node.js server.

4. Works on my machine

A hard-coded path to the Python engine broke the tool on any machine but the original developer's.

Fix: removed machine-specific paths so it runs on any server.

Proving it

To be sure, I independently reconciled 7,561 unique transactions across five overlapping statements for one account, checking every balance by arithmetic rather than trusting any tool's output. That check also exposed defects in a previously used Excel output, which confirmed why verification has to be built in.

Results

  • 250+ statements analyzed in production, from most Indian banks
  • Review time cut from 30+ minutes to under 2
  • No numeric errors reported so far; the few issues seen were in reading account-holder names, not amounts
  • I presented it to the team and manager and walked the sales team through using it

What I learned

The hard part of document AI isn't reading the PDF. It's knowing when you've read it wrong. Building validation into the pipeline, instead of bolting it on later, is what made the numbers trustworthy enough for credit decisions.
